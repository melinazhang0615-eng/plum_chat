# Plum Create V1 后续能力调研与讨论清单

> 文档编号：HANDOFF-06
> 状态：产品讨论底稿，不是排期、API 或数据库合同
> 更新日期：2026-08-10
> 调研参考：Talkie Create、Tipsy Create、Zeta Plot
> 关联文档：[HANDOFF-04](./HANDOFF-04-create-prototype-decisions.md) · [HANDOFF-05](./HANDOFF-05-create-v1-server-integration.md)

## 1. 这份文档解决什么问题

Create V1 已经收敛为一个以 Tipsy 为主要布局参考的**单角色长表单**。本期不做的能力并不等于永久删除：其中一部分是 Plum 长期走向“多角色、世界观、互动小说体验”所需要的结构，另一部分是提升重度创作者效率的工具。

本文把前期对 Talkie、Tipsy 和 Zeta 的调研结果重新归档，用于回答：

1. 哪些能力在竞品中出现，它们服务什么目标。
2. 哪些信息会影响角色回复，哪些只用于公开展示或创作管理。
3. Plum 为什么本期不做，未来重新讨论时需要补齐什么前提。
4. 哪些长期能力需要服务端留出扩展空间，但不应在 V1 预建空字段和空接口。

本文不展开审核与发布状态机。MVP 人审后台、状态、下架和 Runtime 阻断基线见 [HANDOFF-07](./HANDOFF-07-mvp-moderation-and-takedown.md)；拒绝、重提、申诉、自动策略和发布版本继续专项设计。

## 2. 当前产品方向

### 2.1 V1 已确认的入口

- 用户一次创建一个角色。
- 主体是 Name、Gender、Portrait、Character Intro、Opening Scene 和 Character Settings。
- Example Dialogues 与 Response rules 作为选填的高级能力。
- 只上传一张立绘，头像由立绘裁切产生。
- 不提供多角色、世界书、用户身份、声音、对话测试和 AI 图片生成。
- Character card JSON 当前只做浏览器本地导入辅助；TXT 和小说解析只保留未来入口，不选择或上传文件，也不伪造解析结果。

### 2.2 长期方向

- 继续保留单角色作为最简单的创建入口。
- 在单角色之上增加“作品 / Plot”容器，使一个作品可以拥有一个或多个角色。
- 多角色作品再增加世界设定、人物关系、多人发言规则和可选的用户身份。
- 面向酒馆、Tavern 和小说用户提供更强的导入、解析与人工确认流程。
- 对话测试、AI 写作、AI 图片和声音属于创作者工具层，需要在成本、金币、审核和收益确定后再决定优先级。

简化理解：**短期学习 Tipsy / Talkie 的角色创建，长期吸收 Zeta 的作品与互动世界结构。**

## 3. 三个参考产品分别解决什么

以下结论来自本轮需求讨论中查看的创建页与截图，是产品结构总结，不保证竞品之后不会改版。

| 产品 | 创建页的主要对象 | 核心优势 | 对 Plum 的启发 | 不直接照搬的部分 |
| --- | --- | --- | --- | --- |
| Talkie | 单个角色 | 角色创建路径直接；将 Skill、声音和对话测试作为角色能力或创作工具 | 保持角色信息、形象和开场内容是创建主体 | Skill、声音、对话测试不是 Plum V1 所需，不能为对齐竞品而加入 |
| Tipsy | 角色，且提供更完整的长表单和高级设置 | 表单密度适合重度创作者；角色资料、形象、开场、范例和回复设定集中在一页 | Plum V1 的布局、字段组织和 More Settings 主要以此为基准 | 单／多角色类型切换、Voice、对话风格等控件在 V1 删除；避免结构化控件与自由文本规则重复 |
| Zeta | Plot / 作品 / 互动世界 | 从作品层组织多个角色、世界、关系、用户身份和故事运行方式，更接近小说世界体验 | Plum 长期应保留作品层，并允许从 1 个角色自然扩展为多个角色 | 不在 V1 一次性暴露整套复杂结构；先验证单角色创建与消费方向，审核发布另行设计 |

## 4. 能力全景对照

标记说明：`核心` 表示该产品创建逻辑中的明显重点；`有` 表示页面中观察到相关能力；`弱 / 未确认` 表示不是本轮观察重点，不能据此设计合同。

| 能力 | Talkie | Tipsy | Zeta | Plum V1 | Plum 后续态度 |
| --- | --- | --- | --- | --- | --- |
| 单角色资料、形象、开场 | 核心 | 核心 | 有 | 已保留 | 持续作为最简单入口 |
| 单／多角色类型 | 非主要路径 | 有 | 核心 | 不展示类型选择，固定单角色 | 未来由作品自然拥有 1～N 个角色，不必先让用户选“类型” |
| 作品 / Plot 层 | 弱 | 弱于 Zeta | 核心 | 不做 | 长期需要 |
| 主要角色、角色排序 | 弱 / 未确认 | 多角色时相关 | 核心 | 不做 | 多角色阶段需要 |
| 世界设定、人物关系 | 主要塞入角色设定 | 可通过角色设定表达 | 核心 | 只允许写入 Character Settings | 长期拆成作品级结构 |
| 世界书 / 关键词触发设定 | 非本轮重点 | 非本轮重点 | 与 Plot 世界结构相近 | 不做 | 重度创作能力，需单独设计触发与 Token 预算 |
| 用户身份 / Persona | 非本轮重点 | 非本轮重点 | 明显服务于进入 Plot 的身份设定 | 不做 | 多角色和作品入口稳定后再做 |
| Example Dialogues | 有相近表达能力 | 有 | 有相近表达能力 | 已保留 | 持续保留 |
| 回复规则 | 有相近表达能力 | 有 | 可由故事运行规则表达 | 已保留自由文本 | 先观察是否需要结构化控件 |
| 对话风格、回复长度、主动程度 | 有部分创作控制 | 有 | 有叙事运行控制 | 独立控件不做 | 未来需验证是否比自由文本更易用、更稳定 |
| 多人发言规则 | 不适用为主 | 多角色时需要 | 核心 | 不做 | 多角色 Runtime 的必要能力 |
| Skill | 有 | 非本轮重点 | 非本轮重点 | 不做 | 语义和消费场景未定义，暂不进入路线图承诺 |
| Voice / 声音 | 有 | 有 | 非本轮重点 | 不做 | 低优先级，需版权、授权、成本和消费场景 |
| 对话测试 | 有 | 非本轮主要参考 | 非本轮主要参考 | 不做 | 对重度创作者有价值，但先解决成本和隔离语义 |
| AI 图片生成 | 有相关创作能力 | 有相关入口 | 非本轮重点 | 不做 | 先验证纯上传，再评估生成成本与审核收益 |
| 多张角色图、独立作品封面 | 产品能力依版本而异 | 有更完整媒体组织 | 适合作品结构 | V1 只有一张立绘 | 多角色 / 作品阶段再做 |
| JSON / TXT 导入 | 非本轮重点 | Plum 额外强化的方向 | 适合迁移复杂作品 | 仅本地映射 | 后端正式导入是近中期候选 |
| 小说解析为角色和互动故事 | 非标准基础能力 | 非标准基础能力 | 与 Plot 结构高度契合 | 只保留未来入口 | Plum 的潜在差异化能力 |

## 5. 后续模块一：作品与多角色

### 5.1 目标

让用户既可以只创建一个角色，也可以在同一个作品中组织多个角色，而不需要维护两套完全不同的产品。

### 5.2 功能细节

| 功能 | 用户交互 | 是否影响回复 | 消费者是否看到 |
| --- | --- | --- | --- |
| 作品容器 | 创建作品标题、一句话概念和公开介绍 | 公开文字默认不应直接控制回复；是否注入需另定 | 标题、概念、公开介绍可见 |
| 添加角色 | 默认 1 个，未来上限再定；添加、切换、删除角色 | 是，每个角色有独立上下文 | 消费者可在作品页看到登场角色 |
| 主要角色 | 指定一个主要角色 | 影响默认开场和缺省发言角色 | 决定默认封面、卡片和作品入口展示 |
| 角色排序 | 前移、后移或拖动排序 | 可影响默认展示和发言优先级，但不能默认等同 | 可能影响角色列表顺序 |
| 角色独立资料 | 每个角色拥有 Name、Gender、Portrait、Intro、Settings、Examples、Response rules | 是 | 只公开 Name、Portrait、Intro 等公开字段 |
| 角色关系 | 描述角色 A 与 B 的关系，避免复制进多个大文本框 | 是 | 是否公开需按关系条目决定 |
| 作品级开场 | 定义场景、在场角色和首个发言者 | 是，只用于新会话初始化 | 用户进入作品时看到 |
| 多人发言规则 | 每轮谁能发言、最多几人、如何标识角色、是否允许角色互相对话 | 是，属于 Runtime 核心规则 | 用户通过回复形式感知，不一定直接看到规则 |

### 5.3 必须先回答的问题

1. 多角色体验是“群聊”、由系统自动选择发言者，还是用户主动选择角色。
2. 一轮可以有几名角色发言，角色发言以一条合并消息还是多条独立消息返回。
3. 用户在历史聊天中能否新增、移除或替换角色。
4. 主要角色是纯展示属性，还是会影响 Runtime 权重。
5. 首页继续展示主要角色卡，还是新增作品卡类型。
6. 单角色升级为多角色是否保持原有 URL、会话和收藏。

### 5.4 服务端扩展约束

- 长期关系应是 `Work → Characters[]` 或等价结构，而不是永远只有一组固定角色列。
- 每个角色需要稳定 ID；主要角色和排序属于作品与角色的关系。
- 不要求 V1 预建多角色接口，但 V1 迁移不能依赖“作品永远只有一个角色”。
- Prompt 组装要能区分作品级设定、角色级设定和当前发言角色。

## 6. 后续模块二：世界、关系与世界书

### 6.1 三层信息

| 层级 | 示例 | 注入方式 | 公开性 |
| --- | --- | --- | --- |
| 公开世界介绍 | 故事氛围、时代、用户能体验什么 | 默认不作为硬规则；是否用于轻量上下文待定 | 公开 |
| 核心世界设定 | 永远成立的事实、物理规则、共同历史、故事前提 | 每次或按会话缓存进入核心上下文 | 私有或部分公开 |
| 世界书条目 | 地点、组织、物品、都市传说、隐藏规则 | 关键词或语义命中后按需注入 | 默认私有，可逐条决定 |

### 6.2 世界书条目建议能力

- 条目名称。
- 一个或多个触发关键词；未来可扩展为语义触发。
- 设定内容。
- 启用 / 停用。
- 优先级、互斥或分组规则。
- 生效范围：整个作品、指定角色或指定场景。
- 创作者可看到“本轮触发了哪些条目”的调试信息，但消费者不应看到内部 Prompt。

### 6.3 为什么不能直接塞进 Character Settings

- 多个角色会重复保存同一世界信息，容易漂移和冲突。
- 所有设定每轮全量注入会浪费 Token，并挤压聊天历史。
- 世界书需要触发、优先级、版本和调试能力，一个大文本框无法表达。
- 公开世界介绍与私有运行规则需要不同的权限和 DTO。

### 6.4 待讨论

1. 首版世界书只做关键词，还是直接做语义检索。
2. 多个条目同时命中时如何控制 Token 预算和优先级。
3. 是否允许用户在聊天中查看已经发现的世界信息。
4. 世界条目修改后，旧会话继续旧版本还是立即更新。
5. 世界设定是否支持从小说导入候选结果一键创建。

## 7. 后续模块三：用户身份 / Persona

### 7.1 目标

Zeta 式 Plot 不只需要定义“角色是谁”，还需要定义“用户以谁的身份进入”。Persona 可以减少每次开聊都重新解释用户身份、能力和与角色关系的成本。

### 7.2 候选能力

- 默认“以自己进入”，无需填写 Persona。
- 创作者可提供一个或多个预设身份。
- Persona 名称、公开说明或选择提示。
- 用户背景、能力、边界和已知信息。
- Persona 与每个角色的关系。
- 用户进入作品或创建新会话时选择身份。
- 会话创建后固定 Persona 快照，避免编辑影响历史聊天。

### 7.3 数据与隐私边界

| 数据 | 是否影响回复 | 消费者可见性 |
| --- | --- | --- |
| Persona 选择名称与简介 | 名称可能进入上下文 | 选择页可见 |
| Persona 背景与能力 | 是 | 可由创作者决定是否完整展示 |
| 与各角色关系 | 是 | 可只展示摘要，内部细节不公开 |
| 用户自行创建的私人 Persona | 是 | 只属于用户，不应暴露给作品创作者或其他用户 |

### 7.4 为什么 V1 不建占位字段

Persona 的所有权、隐私和会话绑定比普通角色字段复杂。在进入方式没有确定前预建一个 `user_persona_text` 大字段，会阻碍未来同时支持创作者预设身份与用户私人身份。

## 8. 后续模块四：故事运行与结构化控制

V1 已有 Example Dialogues 和自由文本 Response rules。下列结构化控件本期删除，但可以在有运行数据后重新评估：

| 能力 | 价值 | 风险 / 讨论点 |
| --- | --- | --- |
| 对话／叙事风格 | 降低不会写 Prompt 的用户门槛 | 与 Example Dialogues、Character Settings 重叠；预设含义容易模糊 |
| 回复长度 | 简单控制消费节奏和 Token | 模型不一定严格遵守；固定长度可能损害剧情 |
| 主动程度 | 控制角色推进剧情还是等待用户 | 需要可测试的语义，避免角色替用户行动 |
| 高级 Prompt | 给酒馆和重度创作者更大自由度 | 安全、Prompt 注入、字段冲突和迁移成本高 |
| 多人发言规则 | 多角色体验不可缺少 | 必须与消息协议、流式输出和 UI 一起设计 |
| 故事阶段 / 剧情节点 | 支持互动小说和长期剧情 | 状态机、分支、回滚和生成逻辑复杂 |

重新引入结构化控件前，需要通过真实角色样本对比“自由文本能否达到效果”，避免为视觉完整度添加没有稳定 Runtime 语义的选项。

## 9. 后续模块五：导入与小说解析

### 9.1 JSON / TXT 正式导入

当前 V1 只在浏览器本地映射 Character card JSON。TXT 后端接口仅预留并返回 `501 creator_text_import_not_implemented`；前端不调用，也不读取 TXT。正式能力还需要：

- 明确支持的 card 版本、字段和编码。
- 在写入草稿前展示字段映射结果。
- 冲突字段逐项选择覆盖、追加或跳过。
- 不认识的扩展字段保留原始信息供下载，或明确提示丢弃。
- 图片、内嵌 Base64、世界书和扩展 Prompt 分别处理。
- 用户确认后才写入 Plum 草稿，原文件不应默认永久保存。

### 9.2 小说解析

目标不是把整本小说直接塞入 Character Settings，而是形成可编辑的候选结构：

```text
上传文件
  → 异步解析文本与章节
  → 候选角色 / 人物关系 / 世界设定 / 剧情节点
  → 用户逐项选择、合并和修改
  → 生成一个或多个 Plum 草稿
```

需要专项解决：

- TXT、Markdown、EPUB 等输入范围和大小限制。
- 文件版权、授权声明、保存期限和删除。
- 长文本解析的 Token / 金币成本、预估和失败退款。
- 异步进度、暂停、重试和部分结果恢复。
- 同名角色合并、别名、时间线和关系冲突。
- 原著角色与用户原创角色的公开发布权利。
- 解析结果只是候选，必须由用户确认后才能写入正式字段。

该能力与 Zeta 式作品、角色关系和世界书结构高度相关；在目标数据结构确定前，不宜先实现只能输出单个大文本框的解析器。

## 10. 后续模块六：创作者测试与 AI 辅助

### 10.1 对话测试

**用户价值：**在发布前判断角色是否像设定、开场是否自然、回复规则是否生效。

候选交互：

- 使用当前未发布草稿创建隔离的测试会话。
- 清楚显示本轮使用的草稿版本。
- 一键清空、重新开始或切换测试 Persona。
- 测试消息不进入真实聊天历史、热度、推荐和消费者分析。
- 提供“发现问题 → 返回对应字段修改”的快捷入口。
- 可选展示本轮 Token / 金币估算，但不暴露私有模型实现细节。

必须先决定：免费额度、真实扣费、失败退款、滥用限制、测试内容审核、草稿 Prompt 日志保护，以及测试通过是否与发布有任何关系。测试结果不能被描述为审核通过。

### 10.2 AI 写作辅助

候选动作包括生成 Character Intro、压缩 Character Settings、改写 Opening Scene、补充范例对话、检查字段冲突。每次操作都应：

- 由用户主动触发并预览差异。
- 不自动覆盖已有内容。
- 标明预计金币或免费次数。
- 允许撤销。
- 不把私有人设用于其他用户训练或公开展示。

### 10.3 成本与收益判断

重度创作者可能高度需要测试与辅助，但使用频次远低于普通聊天，模型调用又长且昂贵。上线前应测量：

- 有多少创作者完成复杂角色后愿意测试。
- 测试是否显著提高发布率、首聊留存或付费。
- 平均每个发布角色消耗多少 Token / 金币。
- 免费测试是否容易被当作普通聊天绕过收费。

## 11. 后续模块七：媒体、AI 图片与声音

### 11.1 多图和作品封面

V1 只有一张 Portrait。未来可以讨论：

- 每个角色多张图片及排序。
- 独立作品封面；未设置时使用主要角色第一张图。
- 每张图的裁切、用途和审核状态。
- 首页卡、作品页、头像和聊天背景分别使用哪张图。
- 替换图片后旧资源、收藏卡片和会话缓存如何更新。

### 11.2 AI 图片生成

候选流程：输入或从角色设定生成提示词 → 展示金币与内容规则 → 用户确认 → 异步生成 → 选择结果 → 裁切 → 保存为媒体。

必须先确定生成成本、失败退款、并发限制、未成年人和成人内容规则、参考图权利、生成图公开授权、审核时机和删除策略。V1 不提供模拟按钮，避免用户误以为能力已上线。

### 11.3 Voice

可能包括声音库选择、试听、上传、声音克隆和角色语音回复。它不是简单增加一个上传字段，至少需要：

- 声音本人或权利人的明确授权与可撤回记录。
- 防冒充、公众人物和未成年人保护。
- 试听、生成和聊天播放的计费方式。
- 多语言、情绪、语速和长文本效果。
- 声音下架后历史内容的处理。
- 消费者端是否真的有稳定语音使用场景。

因此 Voice 暂列低优先级候选，不因 Talkie / Tipsy 已提供就默认进入 Plum 路线图。

### 11.4 动态形象

GIF、MP4、Live2D 或其他动态形象需要独立的性能、转码、审核、存储和移动端体验设计。当前不是静态图片格式扩展，不应混入 Create V1 图片上传合同。

## 12. Talkie Skill 的处理

本轮只确认 Talkie 创建页存在 Skill 相关能力，但 Plum 尚未定义它对应什么消费者价值。它可能指角色能力、互动玩法、可触发行为或创作者扩展模块，这些语义不能仅凭字段名称推断。

在重新讨论前需要先回答：

1. Skill 是 Prompt 片段、工具调用、剧情机制还是可复用插件。
2. 用户如何触发和感知 Skill。
3. Skill 是否需要权限、外部 API、金币或安全审核。
4. Skill 与世界书、回复规则和高级 Prompt 是否重复。

因此当前状态是“保留竞品观察，未形成 Plum 需求”，不要求服务端预留 `skills` 空表或 JSON 字段。

## 13. 推荐讨论顺序（尚未排期）

| 顺序 | 议题 | 原因 |
| ---: | --- | --- |
| 1 | 审核与发布专项 | 决定角色何时可用、可见和进入 Runtime，是 V1 闭环前置问题 |
| 2 | 正式 JSON / TXT 导入 | 与当前 V1 入口连续，能服务冷启动和现有酒馆用户 |
| 3 | 作品层与多角色消费形态 | 决定 Zeta 式长期结构和服务端扩展方向 |
| 4 | 世界、关系、世界书与 Token 策略 | 依赖作品层，也直接影响回复质量和成本 |
| 5 | Persona 与会话入口 | 依赖作品及多角色交互形态 |
| 6 | 小说解析 | 依赖角色、关系、世界和剧情节点的目标结构 |
| 7 | 对话测试与 AI 写作 | 依赖稳定 Runtime、金币和安全策略 |
| 8 | 多图、AI 图片、Voice、动态形象 | 依赖明确的消费价值、成本和媒体审核能力 |
| 9 | Skill | 先定义产品价值和消费者交互，再决定是否进入路线图 |

这个顺序只是讨论建议，不代表开发排期。可以根据冷启动内容生产、用户反馈和工程资源调整。

## 14. 与同事对齐时需要达成的决定

### 产品

- Plum 的长期一级对象是 Character 还是 Work / Plot；单角色如何作为 Work 的简单形态存在。
- 多角色究竟提供什么消费者体验，而不只是 Create 页能添加多个表单。
- 哪些内容公开、哪些进入模型、哪些仅供创作者管理。
- Persona、世界书、故事节点的最小可用范围。
- 导入、测试、AI 和 Voice 各自解决的真实用户问题及优先级。

### Runtime

- 作品、世界、角色、Persona、世界书和历史消息的 Prompt 分层顺序。
- 多角色发言协议和流式消息格式。
- 世界书触发、Token 预算、冲突和调试。
- 草稿测试与真实会话的隔离。
- 内容编辑后的版本与已有会话绑定。

### 数据与接口

- 只要求 V1 不封死未来；不根据本调研文档直接创建所有未来表。
- 等模块产品语义确定后再设计正式实体、所有权、版本、删除和迁移。
- 公开 DTO、创作者 DTO 和 Runtime 内部数据必须分离。
- 导入原文件、解析候选和用户确认后的正式数据需要不同生命周期。

### 成本与安全

- 哪些能力消耗金币、如何预估、失败是否退款。
- 上传、解析、测试、生成和 Voice 的审核边界。
- 私有人设、用户 Persona、小说原文和测试聊天的隐私与日志规则。
- 未成年人、成人内容、版权、声音授权和下架处理。

## 15. 明确不应发生的事情

- 不因“未来可能多角色”就在 V1 页面增加无效的单／多角色开关。
- 不把世界、关系、Persona 和角色人设永久合并成一个无法迁移的大文本字段。
- 不先做小说解析，再寻找解析结果应该落入什么结构。
- 不用模拟对话、模拟扣币或模拟审核结果冒充真实能力。
- 不把竞品字段名称直接复制成 Plum 的数据库字段。
- 不因为竞品具备 Voice、Skill 或 AI 图片就默认它们对 Plum 有同等收益。
- 不在审核发布专项完成前实现临时状态机和临时发布端点。
