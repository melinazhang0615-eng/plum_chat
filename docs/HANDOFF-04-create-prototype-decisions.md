# Create 原型阶段需求决定

更新日期：2026-08-10

## 原型迭代背景

- `/create` 与 `/create/all-in-one` 保留此前针对作品、世界书和多角色的需求研究，不代表第一期上线范围。
- 当前第一期候选方案调整为单角色创建，以角色形象、公开描述、开场语和核心人设为主体。
- 第一阶段不支持用户身份、多角色创建、角色声音和对话测试，候选页不提供相应操作入口。
- 当前原型仅使用浏览器本地草稿，不代表正式 API 或数据库合同。
- 审核与发布流程单独设计；当前 `Create` 操作只用于表单完整性讨论，不代表真实提交、审核或上线。
- 本期暂缓但可能在后续讨论的竞品能力，集中记录在 [HANDOFF-06](./HANDOFF-06-create-post-v1-research-backlog.md)。

## 后续扩展约束

- 正式后端模型不能把作品永久绑定为单角色结构。
- 用户身份未来应作为作品下可选的独立实体扩展，并允许描述其与多个角色的关系；第一阶段不创建相关表、接口或空字段。
- 数据库和 API 方案在 Create 全部产品需求确认后统一设计，避免依据当前原型提前固化。

## 对照页面

- `/create`：分区说明版，用于查看需求结构。
- `/create/all-in-one`：一页式工作台，用于讨论最终布局与交互。
- `/create/v1`：第一期单角色候选页，以 Tipsy Create 的长表单、媒体入口、右侧实时预览和底部操作栏为主要布局参考。

## 第一期间选页（`/create/v1`）

### 保留能力

- 只上传一张角色立绘；头像始终由该立绘裁切生成，不提供单独头像上传。创作者可以拖动图片调整圆形头像的取景位置，并用方向键微调；裁切位置随草稿保存。
- Name、Gender、Character Intro、Opening Scene 和 Character Settings。
- More Settings 中只保留范例对话和自由文本回复规则。
- Limited / Limitless、Public / Private、标签、成人确认与内容权利确认。
- 浏览器本地自动保存、手动保存、示例填充、重置和表单完整性检查；不模拟真实发布结果。

### 页面顺序与布局

- 主表单先填写 Name / Gender，再创建角色形象，然后填写 Character Intro、Opening Scene 和 Character Settings。
- Gender 不预设默认值，只提供不可选的提示项；第一期可选值固定为 Male、Female 和 Non-binary。
- Character card JSON、TXT 和小说入口不插入主表单，也不常驻为侧栏；统一收进页面右上角的“导入已有内容”动作。
- 点击导入动作后按需展开三个入口；移动端使用居中的紧凑弹层，避免占用主表单首屏。
- Tags 使用最多 5 项的多选控件，不允许自由文本输入；帮助文案需要强调标签会影响搜索和推荐发现。正式标签候选及分类体系由产品后续提供，当前原型只保留选择器结构和旧草稿标签 Chip。
- 竞品标签截图的逐项转录与后续讨论问题记录在 `docs/COMPETITOR-TAG-REFERENCES.md`，当前不能直接视为 Plum 的正式候选标签。

### 必填逻辑

- 01：Name、Gender。
- 02：Portrait；Avatar 自动由 Portrait 裁切生成，不是第二个必填项。
- 03：Character Intro、Opening Scene、Character Settings。
- 04：至少一个 Tag、Content rating、Visibility、18+ 确认和图片／内容权利确认。
- More Settings 中的 Example Dialogues 和 Response rules 均为选填。
- Create 按钮只有在以上必填项全部完成后才可用。由于正式标签选项尚未提供，新空白草稿当前无法完成 Tags 必填项。

### 明确删除

- 不提供单角色/多角色类型选择；第一期前端固定创建单角色。
- 不提供 Voice、声音上传、声音克隆或声音选择。
- 不提供对话测试。
- 不提供 AI 图片生成、模拟生成流程、GIF/MP4 动画上传或动态形象入口。
- 不提供独立的回复长度和主动程度选项。
- 不提供独立的“对话风格”选项；创作者可以通过范例对话和自由文本回复规则表达需要的效果。

### 导入入口

- Character card JSON 作为一级入口，当前原型在浏览器本地兼容 `data` 包装或根节点中的 `name`、`description`、`personality`、`scenario`、`first_mes`、`mes_example`、`system_prompt`、`post_history_instructions` 和 `tags`。
- TXT 和小说保留显眼的未来能力入口，但当前不允许选择、读取或上传文件，也不展示任何模拟解析结果。
- 小说解析的目标产物是候选角色、人物关系、世界设定和可互动剧情节点，必须提供创作者确认流程，不能简单把整本小说塞入角色 Prompt。

### 正式实现约束

- 当前只有 Character card JSON 映射和本地草稿属于前端原型；TXT 后端预留接口 `POST /creator/imports/text` 固定返回 `501 creator_text_import_not_implemented`，不读取、解析或持久化文件。
- 第一版 UI 固定单角色，但服务端的数据模型不应把作品永久设计成只能拥有一个角色；后续应允许作品关联多个角色并指定主要角色。
- 小说导入未来应采用“上传 → 异步解析 → 候选结果 → 人工确认 → 创建作品”的独立任务流程，并考虑文件版权、大小限制、解析成本和失败重试。

### 消费者预览约束

- Create 页不能虚构独立的角色详情页、手机框、消息输入框或尚不存在的消费者交互。
- 第一版 Create 只预览静态主页角色卡片，不预览聊天页；未发布角色不能从预览进入聊天。
- 预览卡片不展示互动热度，也不提供悬停详情或 `Chat Now`；只映射角色名称、封面、标签和公开描述。
- Character Intro 在卡片底部使用更大的固定区域，内容超出时允许在区域内纵向滚动；Character Settings、范例对话和回复规则不进入公开预览。
- 当首页角色卡片的消费者 UI 发生变化时，Create 预览必须同步更新；正式开发阶段优先抽取共享展示组件，避免两处结构长期漂移。
